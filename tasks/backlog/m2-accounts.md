# M2 — Accounts

**Goal.** Give money somewhere to live. Spec §5 wants Cash, Bank, GCash, Maya,
credit card, and savings accounts, each with a balance the user can trust. The
interesting design work here is that **balance is not a stored column** — it is
derived from an opening balance plus the signed sum of transactions, so it can
never drift out of agreement with the transaction ledger. M2 also settles the
delete question: an account with history is archived, not deleted, because
deleting it would silently rewrite the user's past. The demo is spec §31's first
success question made answerable: create Cash + Bank + GCash, see balances,
edit, delete.

## Exit criteria

- [ ] A user can create, view, edit, archive, and delete accounts
- [ ] Deleting an account that has transactions is **blocked** and the UI offers archive instead
- [ ] Balances are derived, correct for both legs of a transfer, and index-backed
- [ ] pgTAP proves user B cannot read, update, delete, or insert into user A's accounts
- [ ] Two accounts cannot share a name case-insensitively within one user
- [ ] Opening balances are entered as decimal text and stored as integer minor units
- [ ] Spec §31 Q1 — "How much money do I have?" — is answerable in the UI
- [ ] Account detail renders a transaction-history region that is empty until [M3](m3-transactions-and-categories.md)

## Notes

- **Derived balance is the load-bearing decision.** A stored `balance` column
  would need every transaction write to update it transactionally and would
  drift the first time a migration or a manual fix touched transactions
  directly. [M2-B02](#tasks) makes drift structurally impossible. Spec §5 and
  §22 list `balance` as an account field; this backlog implements it as
  `opening_balance_minor` plus the view, which satisfies the requirement
  without the drift.
- **Ordering caveat on [M2-B02](#tasks):** the view references `transactions`,
  which lands in [M3-B03](m3-transactions-and-categories.md). Either sequence
  the view migration after M3's table or land it in M2 against a table created
  with only the columns the view needs. Decide this in the issue, not in
  review.
- Sequencing: B01 → B03 → B04 (unblocks all frontend) → B05 → B06 → B02 →
  frontend → B07.
