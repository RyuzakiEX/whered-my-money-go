# M1 — Auth & Profile

**Goal.** Make a user exist. Every financial record in this product belongs to
exactly one user (spec §24), so the `profiles` row and the RLS machinery that
isolates it are the foundation everything else is built on. M1 delivers sign-up,
login, logout, password reset, and a profile carrying the currency and timezone
preferences that spec §4.1 asks for — plus the reusable pgTAP isolation harness
that every later milestone's RLS test builds on. The demo is deliberately
boring: sign up → land on an empty dashboard → log out → log back in.

Two things get established here that are hard to retrofit: **uniform auth error
messages** that never reveal whether an email is registered, and the rule that
**ownership comes from the session, never from input**.

## Exit criteria

- [ ] Sign up → dashboard → log out → log back in works against local Supabase and a preview deployment
- [ ] A `profiles` row is created automatically on `auth.users` insert with currency `PHP` and timezone `Asia/Manila`
- [ ] `profiles` has RLS with a passing pgTAP isolation test
- [ ] The reusable "table is user-isolated" pgTAP assertion exists, is documented, and is used by the `profiles` test
- [ ] Every auth failure path returns a uniform message that does not leak account existence
- [ ] Unauthenticated `(app)/**` redirects to `/login?next=…`; authenticated `(auth)/**` redirects to `/dashboard`; both have integration tests
- [ ] A user can change their display name, currency, and timezone and the change survives a reload
- [ ] All auth pages are axe-clean and keyboard-navigable

## Notes

- **[M1-B03](#tasks) is the highest-leverage task in this milestone.** Every
  later milestone's RLS test is one call to its reusable assertion. Getting the
  harness right here means M2 through M8 each spend one small task on isolation
  testing instead of one large one.
- **Uniform auth errors are a security requirement, not a copy preference.** A
  login form that says "no account with that email" is an account-enumeration
  oracle. [M1-B05](#tasks) and [M1-F02](#tasks) must not disagree about this.
- Sequencing: B01 → B02 → B03 in a chain; B04 lands early and unblocks all five
  frontend tasks; B05 → B06 → B07 in parallel with the frontend; B08 last.
