# Glossary

**Why this exists:** the same concept called three things across a spec, a doc,
and a function name becomes three concepts in someone's head. This file fixes
one name per idea, and code is expected to use it.

Terms marked ⭐ are product differentiators (spec §29).

## Money and amounts

| Term | Definition |
|---|---|
| **Minor unit** | The smallest denomination of a currency — a centavo for PHP. All money is an integer count of these. `₱1,234.56` is `123456`. See [ADR-0005](../adr/0005-money-as-integer-minor-units.md). |
| **`Minor`** | The TypeScript type alias for an integer minor-unit amount. Columns carry a `_minor` suffix. |
| **Largest-remainder allocation** | Splitting an amount so the parts sum exactly to the whole — distributing leftover minor units to the largest fractional remainders. Used for category percentage shares. |
| **Signed amount** | An amount with direction applied. Stored amounts are always positive; the sign comes from the transaction type. |

## Accounts and balances

| Term | Definition |
|---|---|
| **Opening balance** | The stored starting balance of an account (`opening_balance_minor`). Set once at creation. |
| **Current balance** | Opening balance plus the signed sum of that account's transactions. **Derived, never stored** — see [data-model.md](../architecture/data-model.md#derived-views). |
| **Spendable account** | An account counted toward Safe to Spend — `exclude_from_safe_to_spend = false`. |
| **Excluded account** | Deliberately kept out of Safe to Spend, typically long-term savings. The money exists; it is not in play. |
| **Liability balance** | A credit-card or loan balance, negative when money is owed. Enters Safe to Spend as that negative value — **never** as available credit. |

## Time

| Term | Definition |
|---|---|
| **Calendar date** | A date with no time and no timezone (`2026-09-09`). **Not** an instant. All recurrence and period math uses these. See [recurrence.md](../domain/recurrence.md#the-timezone-rule). |
| **`today`** | The current calendar date in the user's timezone, always **injected** into domain functions, never read from the clock. |
| **Period** | A budget period — the calendar month in the MVP. |
| **`periodStart` / `periodEnd`** | First and last calendar dates of the current period. Both inclusive. |
| **Horizon (`H`)** | The forward-looking window a calculation considers. Safe to Spend uses `[today, periodEnd]`; the Timeline uses `[today, today + N days]` for N ∈ {7, 30, 60, 90}. |
| **`daysElapsed`** | Inclusive days from `periodStart` to `today`. **Is 1 on the first of the month**, never 0. |
| **Anchor day** | The day-of-month a monthly recurrence targets. Preserved across clamping: Jan 31 → Feb 28 → **Mar 31**. |

## Transactions

| Term | Definition |
|---|---|
| **Actual** | A transaction that has happened — `occurred_on <= today`. The only kind counted in spending totals, budget progress, and balances. |
| **Scheduled transaction** | A real row with `occurred_on` in the future. Not yet spending; an input to Safe to Spend and the Timeline. The MVP's substitute for the V2 recurrence engine. |
| **Occurrence** | A single instance generated by expanding a recurring rule over a date range. Not a stored row. |
| **Materialised occurrence** | An occurrence that has become a real transaction. |
| **Dedupe** | Dropping an expanded occurrence when a matching actual already exists — so rent paid early is counted once. Matched on `(recurring_transaction_id, periodKey)`. |
| **Transfer** | Money moved between the user's own accounts. Two paired legs sharing a `transfer_group_id`. **Excluded** from spending, income, and the Timeline — moving money is not spending it. |
| **Transfer group** | The two legs of one transfer, created and deleted together. |

## Safe to Spend ⭐

| Term | Definition |
|---|---|
| **Safe to Spend** ⭐ | What the user can spend without breaking an existing commitment: current balance + expected income − upcoming expenses − planned savings − debt payments, over the horizon. Spec §9. |
| **Committed outflow** | The three subtracted terms together — money already promised. |
| **Expected income** | Income due within the horizon and not yet received. A forecast, not a fact. |
| **Upcoming expenses** | Committed outflows within the horizon, deduplicated against actuals. |
| **Planned savings** | Remaining goal contributions needed this period: `max(0, monthlyTarget − contributedThisPeriod)` per goal. |
| **Debt payments** | Minimum payments due within the horizon. Separate from upcoming expenses because users think about debt separately. |
| **Term** | One line of the Safe to Spend identity, carrying its own total and its contributing items. |
| **Breakdown** | The full set of terms with their contributions — what makes the number explainable, and therefore trustworthy. |
| **Status band** | 🟢 / 🟡 / 🔴, relative to the user's income scale rather than an absolute threshold. |

## Money Timeline ⭐

| Term | Definition |
|---|---|
| **Money Timeline** ⭐ | Upcoming money events in chronological order, each with the balance after it lands. Spec §10. |
| **Timeline event** | One dated inflow or outflow within the horizon. |
| **Projected balance** | The running balance after each event — a fold seeded with the opening balance. **The column that turns a bill list into a forecast.** |
| **Shortfall date** | The first date the projected balance goes negative, or `null`. The feature's real payoff. |
| **Occurrence cap** | `MAX_TIMELINE_EVENTS` — bounds recurrence-expansion CPU. Truncation drops the latest events and is disclosed to the UI. |

## Budgets

| Term | Definition |
|---|---|
| **Budget** | A spending limit for one expense category in one period. |
| **Spent** | Actuals in that category and period. Excludes transfers and scheduled transactions. |
| **Remaining** | `budget − spent`. **May be negative** — that negative is the overspend, and is never clamped. |
| **Run rate** | `spentToDate / daysElapsed` — the current daily pace. |
| **Historical shape** | How a category's spending has historically distributed across a month. Captures rhythm a flat rate cannot. |
| **Blend weight (`w`)** | `min(1, daysElapsed / 10)` — how much to trust the current period over history. Ramps as evidence accumulates. |
| **Projected** | Estimated period-end total. Never less than what is already spent. |
| **Confidence** | `low` / `medium` / `high`. Low projections must not be rendered as precise figures. |
| **Budget status** | `on_track` / `at_risk` / `over` / `exceeded`. **`exceeded` outranks all** — it is the only one based on fact rather than forecast. |

## Goals

| Term | Definition |
|---|---|
| **Goal** | A savings target with an amount and optionally a date. Spec §13. |
| **Contribution** | Money added toward a goal. A row in `goal_contributions`, optionally linked to a transaction. |
| **Current amount** | Sum of contributions. **Derived, not stored.** |
| **Required monthly contribution** | `(target − current) / monthsUntil(targetDate)`. |
| **Projected completion date** | When the goal completes at the observed contribution rate. `null` — *"at this rate, never"* — when the rate is not positive. |
| **Goal ETA** | Shorthand for the projected completion date. |
| **Goal Impact** ⭐ | How a spending change shifts a goal's projected date, in days. Spec §14. |
| **What-If** ⭐ | Re-running the same pure functions with perturbed inputs. Spec §18. **Needs no new math** — only an input-override layer. |

## Architecture

| Term | Definition |
|---|---|
| **`lib/core`** | Pure, dependency-free domain logic. No React, Next, supabase-js, Zod, date library, `process.env`, or clock. [ADR-0003](../adr/0003-pure-typescript-domain-core.md). |
| **`lib/server`** | Server-only data access — Supabase clients, queries, Server Actions, mappers. |
| **Mapper** | Converts a database row to a domain type. Rows never reach `lib/core` or components. |
| **Domain type** | A type shaped by the product. Distinct from a generated database row type, which is shaped by Postgres. |
| **Contract task** | A `type:contract` task landing migration + generated types + Zod schemas + domain types. **Blocks** its milestone's frontend tasks. |
| **Stream** | `frontend` / `backend` / `shared` / `devops` — a label, not a team. Ownership is by directory. |
| **Cache tag** | A namespaced invalidation key, always `user:{id}:…`, always a constant. |
| **Aggregate gate** | A CI job with `if: always()` that fails only on real failure — the required status check, so skipped jobs never block a PR. |
| **Preflight** | The CI job detecting what the repository contains, so code jobs skip gracefully while it is docs-only. |

## Security

| Term | Definition |
|---|---|
| **RLS** | Row Level Security. Postgres policies restricting which rows a user may read or write. The primary isolation mechanism. |
| **`auth.uid()`** | The current user's id inside a policy, from their JWT. |
| **Default-deny** | RLS enabled with no matching policy: access refused. Fails closed. |
| **Cross-table ownership** | Verifying a referenced foreign key also belongs to the user. **A naive `WITH CHECK (user_id = auth.uid())` does not do this** — see [rls-policies.md](../architecture/rls-policies.md#cross-table-ownership). |
| **The three-layer rule** | Identity from the session → application ownership re-check → RLS. Each catches a different failure. |
| **`service_role`** | The Supabase key bypassing all RLS. Never reachable from `app/`; never a GitHub Actions secret. |
| **Anon key** | The public Supabase key. Public **by design** — RLS protects the data, not this key's secrecy. |

## Deprecated names

Do not use these; they mean something else here, or nothing:

| Avoid | Use instead | Why |
|---|---|---|
| `balance` (as a stored column) | `opening_balance_minor` / current balance (derived) | A stored mutable balance drifts |
| `amount` (bare) | `amount_minor` | Ambiguous about units — the dangerous kind of ambiguous |
| `date` (as a column) | `occurred_on` | `date` is a SQL keyword |
| "available to spend" | "Safe to Spend" | One name for the feature |
| "forecast" (unqualified) | "projected total" (budget) or "projected balance" (timeline) | Two different calculations |
| "recurring transaction" (for an expansion) | "occurrence" | The rule and its instances are different things |
